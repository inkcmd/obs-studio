# XINKX Studio — Native stream and portrait editor (Windows runtime verification pending)

## Broadcast tags — Twitch, Kick and YouTube (Windows verification pending)

- The **Эфир** editor has native add/remove tag chips. **Twitch / Kick** share up to ten tags of at most 25 Unicode letters/numbers each, without spaces or punctuation. **YouTube** has a separate tag list allowing spaces, subject to Google's aggregate 500-character limit. Lists are stored independently in `studio.ini` and in each saved game profile; previously saved profiles without tags still load.
- Twitch writes `tags` via `PATCH /helix/channels`. Kick writes `custom_tags` via `PATCH /public/v1/channels`, then reads them back because a successful HTTP 204 has not always meant tags were applied. Clearing all chips sends an empty array only after the streamer deliberately edits or saves that tag list.
- YouTube video tags use the public `videos.list` / `videos.update` endpoints against the selected broadcast's video ID, **not** `liveBroadcasts.update`. `videos.update` costs 50 quota units, so unchanged tags do not trigger that write. Unchanged broadcast metadata likewise skips `liveBroadcasts.update`. Other video snippet properties are retained where writable.
- Check in a native Windows build with disposable test broadcasts: save and reload tags in two game profiles; add and remove Twitch tags including Cyrillic, reject a space and an 11th tag; compare Kick's channel tags with the request; on YouTube verify multiword tags, a repeated Save without additional writes, and explicit clearing of all tags. Source tests do not verify provider behavior.

## Realtime multichat — YouTube, Twitch, Kick (Windows verification pending)

- **YouTube** receives chat over the documented `liveChatMessages.streamList` gRPC HTTP/2 server stream, using the OBS-linked libcurl and the same OAuth access token. No periodic `liveChatMessages.list` polling remains. The last `nextPageToken` resumes reception after a disconnect; initial history is skipped once, message IDs are deduplicated and multiple RTMP outputs of one YouTube channel share one chat session. Expired/revoked access tokens are refreshed, connections retry with bounded backoff and quota-exhausted errors pause API discovery until the next Pacific midnight. Discovering an active broadcast and updating viewer numbers still use infrequent REST calls; streaming does not eliminate all YouTube quota costs.
- **Twitch** keeps the official EventSub WebSocket. On `session_reconnect`, the replacement socket must receive `session_welcome` before the old one is released. Existing subscriptions transfer and are not recreated during this seamless handoff. Unexpected socket closures and revoked chat subscriptions trigger a retry, while invalid/expired OAuth does not cause a new validation attempt each second.
- **Kick** keeps its existing Centrifugo live WebSocket (Kick's public webhook requires a public listener, unlike this local OBS application). Discovery, guest-token and socket errors retry with bounded exponential backoff. Stale socket callbacks cannot tear down a newer connection.
- **Runtime acceptance:** In a Windows MSVC/Qt/libcurl-HTTP/2 build, open all three chats; send one message to each, temporarily disconnect networking and verify reconnection without duplicate lines. Keep OBS minimized for five minutes and verify chat and audience overlay continue updating. Confirm YouTube OAuth refresh, a new broadcast's chat ID, and a full live session without `403 quotaExceeded`. Twelve Node source-contract tests pass; these do not validate native compilation or live authenticated reception.

## Portrait editor correction — independent layers and native scene-item transforms

- A vertical stream selected in **Settings → Stream** opens its 9:16 preview automatically in OBS's central preview area (also restored at startup); disabling all portrait outputs closes that view on Apply. The preview is limited in width so the horizontal OBS canvas remains usable. The **1080×1920 output boundary** is drawn even when the scene is empty or black; the guide is preview-only. The existing OBS **Sources** dock has **16:9** and **9:16** tabs: the native source tree and toolbar remain intact in the first tab; the portrait source tree and its add/remove/properties controls live in the second. Closing portrait restores the original Sources dock layout.
- Portrait scenes start with **no automatically mirrored sources**. Each OBS scene name has its own list of portrait scene items, layouts and independent source snapshots. Previously saved portrait layouts are migrated once; source layouts are kept separately from the horizontal OBS item transforms. OBS's normal scene selector switches both compositions together.
- **+ Source** offers two explicit choices: reuse an OBS source, sharing its input properties but not its position/size/crop; or make an **independent duplicate** via `obs_source_duplicate` with separate input properties and a persisted source snapshot. Dedicated XINKX overlays can also be created directly on the portrait canvas. Some physical capture devices cannot be opened twice; reuse their existing OBS source in that case.
- Drag and resize work from the **initial mouse-down transform** rather than applying per-frame rounded deltas; scene-item changes are batched to disk. The preview uses a visible selected-item outline and 8 handles, and snaps to canvas edges, centres and other visible layer edges using a threshold proportional to the displayed zoom. The real libobs scene-item APIs remain the transform authority.
- This is still a dedicated portrait preview implementation, not a second `OBSBasicPreview` instance. OBS's stock preview editor is tightly bound to the singleton main scene/source tree and cannot be instantiated twice unchanged. Full parity for native rotation/cropping/group handles and editing shortcuts requires extracting its shared editor context; those gestures are **not** claimed by this patch.
- Verify on a **Windows MSVC/Qt build**: visual canvas boundary, source moves/8-handle resizing/snap at all preview sizes, independent duplicate properties, camera reuse, horizontal/portrait scene switching, restart persistence and 9:16 streaming. Node tests assert source contracts, not Windows rendering.

## Stages 21–23 — RTMP reliability, source catalog editing and native portrait canvas

- **21 / RTMP:** An individual output's restart is scheduled only after its asynchronous stop finishes and `obs_output_active()` becomes false. Rapid off/on requests coalesce; after 10 seconds without reaching an idle state, the request fails visibly rather than starting a second encoder on a stopping output. Global Stop cancels queued restarts. The menu reports the output's encoded video frame count and stop code. `diagnostics.log` records redacted state transitions, not keys, cookies or authorization headers. Two simultaneously enabled outputs pointing to exactly the same RTMP server+key are refused: they cannot safely act as separate horizontal/vertical YouTube feeds. This does not diagnose YouTube's remote transcoder or Live Control Room state; only a real server-side preview/live-state check can confirm that the picture reached viewers.
- **Offline startup / YouTube readiness:** The Chat page's **Обновить** button now retries unavailable Twitch, YouTube and Kick connections without bypassing an actual YouTube daily quota pause. Transient Twitch OAuth validation failures retry with bounded backoff and no false "reauthorize" diagnosis. Visible warnings identify missing Twitch follower/subscriber OAuth scopes. In **Эфир**, select a YouTube broadcast and click **Проверить**: the read-only check displays the broadcast lifecycle, bound ingest status, and whether the configured stream ID/RTMP key match; no key is printed. A healthy local RTMP bitrate alone cannot prove YouTube is showing the correct broadcast. The long-lived YouTube gRPC chat now uses interruptible HTTP/2 polling, so closing a stalled connection does not wait indefinitely for network traffic on the OBS UI thread. RTMP start/restart/stop operations have extra timestamps in `diagnostics.log`. Actual stream availability and UI freeze behavior must still be checked in a Windows build.
- **22 / sources:** The native preset catalog now edits the **existing selected** XINKX source as well as adding a new one. Chat layer dimensions and its two independent background alpha values can be set in the catalog; existing reaction IDs are preserved when updating an existing custom reaction. User presets continue to persist locally. The catalog thumbnails are **style mockups**, while the OBS scene preview is the actual browser/native source output; thumbnail live-rendering is not yet implemented.
- **23 / portrait:** Each account in **Настройки → Трансляция → Изменить** can choose **Видеокомпозиция → Вертикальная композиция 1080×1920**, with a 9:16 encoder resolution (1080×1920 or 720×1280). **Редактировать вертикальную композицию** opens the independent libobs portrait scene's live preview and source list, with per-source X/Y/width/height, fit/fill, visibility and dragging. It reuses source objects from the current OBS program scene but gives them **independent transforms**; no horizontal framebuffer is passed through a 9:16 stretch. Source layouts persist per scene in local `studio.ini`, are restored when switching scenes and change without a streaming restart. The portrait mix is independent, but its source set still follows the current horizontal program scene; an entirely separate scene switcher/collection for portrait is not implemented.

3. Select a disposable 9:16 output (preferably an unlisted YouTube test event with its own stream key), configure its vertical canvas and place the game, camera and chat independently. Change the horizontal scene, verify portrait switches and its saved layer layout restores. Confirm OBS renders both mixes and that YouTube decodes the 1080×1920 picture.
4. In the source catalog, select an installed XINKX chat source in OBS, choose another style and alpha/dimensions, click **Применить к выделенному источнику**; restart the app and verify persistence. Repeat for a reaction with a custom ID.

No automatic YouTube broadcast creation, start or modification is performed by the portrait editor. The account's ordinary OAuth and the other providers are not changed by selecting 9:16 output. An authenticated Windows live test and main-project build remain required for these stages.

## Stage 19 — historical implementation (superseded by Stage 20)

- The **Эфир** tab presents a single profile selector/name/OBS scene, one title, one description, one game autocomplete and one thumbnail. **Сохранить профиль и обновить площадки** is the sole Save/Apply action: it stores the profile, switches to its scene, then updates connected Twitch/Kick/YouTube accounts. Merely selecting a profile changes the local editor, not any live broadcast. A failed scene switch or failed profile file write blocks remote updates.
- A typed game searches the connected Twitch/Kick catalogs and the authenticated YouTube Studio game-title catalog after 700 ms; the single autocomplete merges suggestions. Matching exact provider labels populate per-provider IDs and the YouTube `mid` **without duplicate visible dropdowns**. These IDs are locally preserved per profile, including legacy profiles. When a game cannot be unambiguously mapped on a provider, it does not reuse the previous game's category and reports the limitation. Games with different official titles are not guessed automatically.
- YouTube's regular category **Gaming (`20`) is requested from `videoCategories.list?id=20&hl=ru`**, then applied via the official Live Broadcast API and checked against `videos.list` for the actual video. A successful HTTP response alone is not reported as proof of category change. This is a broad *video category* and does not constitute a specific game's ID. For the game itself, the separate authenticated Studio browser session must be ready and an exact `mid` found. Existing logged-in **XINKX-managed** Chrome/Edge profiles reconnect on app start or another click; the user's unrelated default Chrome profile is intentionally not read. If its windows are open without CDP, close those dedicated windows before reconnecting.
- Video event/RTMP stream creation and binding controls have been removed from **Эфир**, so they do not duplicate **Настройки → Трансляция**. Automatic YouTube event resolution is limited to an unambiguous active event, event bound to the configured output, or only remaining event. Multiple ambiguous events fail safely with an explicit status. The old remote-state block has been removed.
- An image can be chosen and saved with the profile; it is uploaded on Save through official YouTube `thumbnails.set` for the resolved broadcast. JPEG/PNG up to 20 MB are accepted by this implementation. Twitch and Kick do **not** expose a documented equivalent custom live-thumbnail upload API, so their images are not uploaded; the editor reports that limitation. Asynchronous YouTube game and image operations use the snapshot captured when Save was pressed, not subsequent user edits.
- **Not implemented:** a separate native 9:16 YouTube vertical OBS canvas/output. YouTube's own Live Control Room can generate a vertical crop from horizontal input or accept a separate vertical encoder, but configuring an independent vertical canvas in XINKX requires a separate libobs video-compositing path. No stretched horizontal stream is passed off as vertical.

Windows checks: build `cmake --build --preset windows-x64 --parallel 12`; verify a saved profile round-trip, one Save against a disposable YouTube broadcast, the exact game in YouTube Studio, a custom thumbnail on that broadcast, repeated dedicated-profile Chrome reconnection and unaffected Twitch/Kick updates. Do not modify an existing live broadcast for the test without choosing it explicitly. `node frontend/xinkx/tests/youtube-studio-bridge-js.test.mjs` covers the browser-side mock; the source contract test checks UI wiring, but neither replaces a Windows MSVC build or Google/Twitch/Kick runtime authorization test.

## Stage 18 — historical YouTube Studio experiment (removed in Stage 20)

- The native broadcast editor now searches a unified game name on Twitch, Kick and (when the separate Studio session is connected) the unofficial YouTube Studio `gaming/game_title` endpoint. The picker stores YouTube's `mid` alongside the game name locally. Picking a YouTube result maps the regular video category to 20 (`Gaming`). Typeahead search starts after 700 ms without replacing the title/description/game draft.
- **Подключить YouTube Studio** launches the installed Chrome/Edge with an isolated XINKX-managed profile and **without debugging flags** for normal first-time Google login. Close all its windows after login and click **Подключить Studio** again. This reopens the same isolated profile with a loopback-only Chrome DevTools Protocol port and checks Studio's current channel ID against the existing YouTube OAuth account. The session is reopened automatically on subsequent app starts. The regular Chrome/Edge profile and its cookies are never read.
- Search HTTP requests execute inside the authenticated Studio tab and compute authorization from its live state; cookies, hashes and dynamic ytcfg context never leave the browser renderer or enter the XINKX diagnostic log. If the private search endpoint stops accepting these requests, search explicitly fails without touching other accounts.
- The common Save button updates YouTube title, description and category with the official OAuth API first. Only after that succeeds and only with a verified Studio session and explicitly selected `mid`, the browser bridge navigates to the selected video's edit screen, selects its game from the Studio autocomplete and clicks the Studio Save button. It then reloads the editor and compares the selected game label. This uses YouTube's own evolving internal metadata request/attestation instead of constructing an unreliable hardcoded `metadata_update` payload. Name verification does not independently prove an internal `mid` when multiple games share the same exact name; ambiguous suggestions are rejected.
- The Studio browser operation remains optional, asynchronous and independent of OAuth, Twitch, Kick and libobs outputs. An expired session/channel mismatch/failure is visible in the Studio status. It never edits a test or live broadcast automatically: only the common user Save button may modify one. Browser-side selectors/internal endpoints are unofficial and may change; the implementation has **not** yet been validated with an authenticated Windows Studio session or a live test video.

## Stage 16 changes — native sources and broadcast reliability

- Fixed registration of the six `xinkx_*` OBS input types. They were rejected by libobs because a video-only source was incorrectly flagged as `OBS_SOURCE_COMPOSITE` without an audio-render callback. Each XINKX type is now selectable from the standard Sources `+` dialog and manages an active private browser child.
- The broadcast editor now reloads metadata for all connected accounts with one button; one save action can update all accounts. YouTube's general Gaming category is kept when searching for a specific game. Each platform retains its own category ID. Kick uses `channel_description` when returned and displays a placeholder if Kick omits `stream_title`.
- Game profiles now store the scene UUID as well as its display name; renaming an OBS scene refreshes the dropdown without breaking UUID-backed profiles. Legacy name-only profiles migrate on save. If the collection has exactly one scene, a renamed legacy binding can resolve unambiguously.
- Chat send confirmations and provider warnings are recorded to `diagnostics.log` instead of being mixed into the chat history. Settings now have a Diagnostics page. XINKX settings icons are tinted for the dark theme, and the chat appearance editors include a sample message preview.
- The streamer overlay has two independent controls: show/hide and mouse placement mode. In placement mode only the chat area accepts drag input; offsets are saved in `presentation.json`. With placement disabled the full overlay passes clicks to the game again. The streamer display uses platform symbols and animates reaction particles/fades while effects are active.

**Not implemented in this patch:** generic user-supplied effect assets/timelines, arbitrary payment-provider and bank connectors, server-side OAuth for new donation sites, automatic LLM model connection. Native source types still render HTML internally through OBS browser, not via a separately authored GPU shader. Kick may omit title/description fields in its public channels response; the UI cannot restore data that the provider does not return.

Windows MSVC build and end-to-end Kick/YouTube/OAuth runtime checks remain necessary.

Supported commands: `scene.create`, `scene.activate`, `source.text.add`, `source.visible`, `overlay.add`, `effect.trigger`, `timer.start`, `timer.pause`, `timer.hide`. Test JSON in Settings → Stream → Automation. It does **not** start a socket, execute Python, run shell commands or connect a model automatically. A future authenticated local model bridge can dispatch through the same API.

Sample command:

```json
{"command":"overlay.add","layer":"alerts"}
```

## Stream accounts

1. In **Settings → Stream**, add Twitch, YouTube or Kick OAuth accounts; **Каталог OBS · RTMP-сервисы** opens the OBS service catalog (including less-common platforms) and their available ingest servers; **RTMP(S)** accepts an arbitrary server URL. There is no limit on the number of accounts, including accounts from one provider. The catalog is limited to services that work with RTMP or RTMPS: WHIP, HLS and other protocols need separate output implementations.
2. For a catalog service, select both the service and its server and enter the stream key. For a custom RTMP(S) destination, supply the URL and key. For the three integrated providers, supply credentials manually or use OAuth to obtain an ingest URL and key. Each destination has its own encoder, bitrate and output resolution. For native 1440p set both the base and output OBS resolution to 2560×1440.
3. **Every enabled XINKX destination is equal**: the OBS Start/Stop Streaming button starts/stops all configured accounts through their own `libobs` outputs, with no primary or dummy stream and no single-server dependency. Stock OBS Stream settings remain stored, but are used only when the XINKX list is empty. They can be inspected via the checkbox on the accounts panel. The old `primary` flag in Stage 5/6 profiles is ignored for compatibility.
4. Use **Apply** or **OK** to save edits. **Cancel** discards draft edits. OAuth actions require a saved account and persist their result immediately. A revoked grant cannot be restored by Cancel.
5. The account menu next to **Start Streaming** (**Ctrl+Alt+S**) changes which accounts participate without editing their saved defaults. During a session, each output can be stopped individually. The main OBS button stops all outputs. The OBS bottom status bar now shows the session timer, combined bitrate and combined dropped frames even without an active stock OBS output. **Выходы: N/M** shows the current number of transmitting accounts, the aggregate bitrate and per-output details in its tooltip. These are *local* OBS output measurements, not platform playback confirmation.

Each destination has its own `obs_service_t`, `obs_output_t` and encoders. Existing Stage 5/6 account records are compatible. Their ingest URL and key are kept out of the OBS profile's `service.json`; recording and virtual-camera settings still belong to OBS. Account records are read from `config/xinkx-studio/studio.ini`. The stream key, manually entered ingest URL, client secret and OAuth tokens are protected using Windows DPAPI under the current user account. Named catalog services and their public ingest server addresses are stored in plain text.

## Provider OAuth

Enter the credentials for your developer app in the account editor and apply the settings. Use **Подключить OAuth** to authorize in the default browser. The loopback callback is now `http://localhost:8765/api/oauth/{platform}/callback` (`platform` = twitch, youtube, kick). If the default browser has the wrong signed-in account, click **Скопировать ссылку OAuth** and open it in the right browser. **Отменить ожидание** releases the local listener without waiting three minutes. These callback URLs match the legacy web app *if registered exactly as shown*; the old Windows portproxy listener on 127.0.0.1:8765 must be removed or OAuth binding will fail. **Обновить данные** loads account identity and ingest information and refreshes an expired or rejected token when a refresh token is available. **Отключить OAuth** requests provider revocation and clears the local session and OAuth-derived ingest data after success. A manual RTMP key stays available.

- **Twitch** uses a developer app with the loopback redirect URI, Client ID and Client Secret. Permissions include the stream key, broadcast metadata, chat read/send, follower/subscriber events and bits. If a specific optional EventSub subscription (such as cheer) is rejected with HTTP 403, the chat subscription remains connected; check consent/eligibility separately. Existing OAuth grants must be reauthorized after a scope change. [Twitch scopes](https://dev.twitch.tv/docs/authentication/scopes/)
- **YouTube** uses a Google OAuth client of type **Desktop app** with YouTube Data API v3 enabled. Use a channel enabled for Live and add the Google account as a test user if the consent screen is in testing mode. The OAuth scope is now `youtube` (manage channel) instead of `youtube.readonly` to allow live-stream creation and future chat/broadcast management; reconnect OAuth to grant it. In the account editor, **Выбрать / создать** lists available ingestion streams across pages and can create one with a title, resolution and frame rate. ### Distribution and legacy credentials

- A public OAuth **Client ID** may ship with a desktop application, but a confidential **Client Secret** must not be hardcoded in a distributable EXE (DPAPI does not protect embedded constants). A turnkey release requires public-client flows such as PKCE/device authorization where each provider supports them, or a hosted OAuth broker that retains confidential secrets server-side. Until that work is done, the current Twitch/Kick flows still require developer credentials from each operator; Google uses a Desktop OAuth client. Do not copy legacy credentials into source or a Git patch.
- The native OAuth callback reuses the legacy callback path on port 8765. A single process must own this port. DonationAlerts is an **alerts integration**, not an RTMP broadcast destination: it should be integrated through the native account/alerts feature rather than added to the stream-output selector.

## Stage 12 — legacy features consolidated into native frontend (Windows verification pending)

- **Kick real-time chat:** `chatroom.id` from `https://kick.com/api/v2/channels/<slug>` (or user-specified room ID) → guest discovery and authorization → Centrifugo `wss://realtime.*.platform.kick.com/connection/websocket` → `chatrooms.<id>.v2` subscription → unified native chat and viewer overlay. This is deliberately isolated from public Kick webhooks; never claim that a public webhook is required for this chat receiver. Reconnect and refresh are supported. Unsupported, undocumented protocol changes result in a visible status, not silent success.
- **Both overlays:** **Оформление и реакции** controls a viewer OBS Browser Source overlay and a separate topmost, focusless, click-through Windows window for the streamer. The latter is optional and can be toggled without changing what OBS encodes. Both share incoming events and configurable but independently styled `viewer`/`streamer` profiles. Stage 12 saves `presentation.json` atomically; you can edit the whole schema in a validated JSON dialog. Available fields include font, text/name/background colors, size, opacity, alignment, message limit/expiration (0 = persist), effects position (including random), particle range, duration (0 = persist), max concurrency, per-viewer reaction cooldown and a 0 global cooldown for unlimited activation. **Очистить все эффекты** removes persistent effects from both surfaces.
- **Chat bot commands:** Optional entries in `presentation.json`'s `botCommands` array trigger automatic replies through the logged-in broadcaster account on the *same platform*. They are disabled by default (empty list); each has trigger, reply, enabled, cooldownMs and perViewer. This is *not* a separately authorized bot account.
- **Viewer counts:** Twitch Helix, YouTube live video details and Kick public channel API are queried once per minute; unavailable counts display `—` and are never treated as zero. YouTube outputs linked to one OAuth channel share a chat poller and one chat selector; audience counts sum distinct active YouTube live videos only when all report concurrent viewers. The streamer overlay has no OBS window parent, so minimizing OBS does not hide it. The counts are per-video concurrent sessions, not unique people across platforms or simultaneous broadcasts.
- **Broadcast management:** **Управление эфиром** fetches Twitch/Kick channel metadata and available YouTube live broadcasts/streams. Search for a platform category, update title/category on a selected channel, or apply a common title to connected channels. Category IDs are **platform-specific** and are not copied indiscriminately to another platform; game profiles map each provider's ID independently. Twitch and Kick do not expose channel descriptions via the selected endpoints; YouTube broadcast snippet updates preserve the current mandatory scheduledStartTime and other snippet data. Select/create a YouTube broadcast and RTMP stream, or bind an existing stream; binding updates the DPAPI-protected ingest parameters for that account. A newly created YouTube broadcast uses `unlisted` visibility, not public. Provider-side changes happen only on an explicit Save/Create/Bind action or an enabled game-profile automation.
- **Profiles and scene automation:** **Профили игр и сцен** stores `game-profiles.json`, referencing a *real OBS scene by name* plus per-platform category IDs, title, description and YouTube broadcast ID. **Активировать** switches the actual OBS scene and updates the platform APIs; optional scene-change automation is **off by default**. **JSON сцены OBS** loads the current scene's real scene-item IDs and editable positions, scales, rotation, crop, visibility and locking into JSON, validates each object, then applies edits through libobs and adds a native Ctrl+Z undo action. Changing the number of sources while editing blocks the operation. Source creation, media assets and the scene graph still live in OBS scene collections; there is no parallel XINKX JSON scene renderer.
- **DonationAlerts:** **Донаты** has its own localhost-only OAuth callback at `http://127.0.0.1:8767/oauth/callback` (register exactly this in the DonationAlerts developer app), requesting `oauth-user-show oauth-donation-index oauth-donation-subscribe`. Tokens/secret use Windows DPAPI. New donations are polled on the provider's REST API every 15 seconds, with a first-load baseline that prevents historical donations from firing alerts. Donor names and donation amounts flow through the same stage-10 overlay cards; no external webhook, Node.js process or Kubernetes installation is needed. This is REST polling, not sub-second push delivery.

The old legacy 0.14.5 web UI/API remains useful reference material, but this native patch does not import the Electron window, Kubernetes backend or a second OBS scene graph. It does not yet implement third-party donation providers, separate bot OAuth identities, moderation interfaces, an animated JSON scene-asset timeline, or a full visual designer for custom alert sounds.

```json
  "reactions": [
```
